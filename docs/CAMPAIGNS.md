# Invite.md — Campaigns and Personalized Invitations

Status: Proposed.

## 1. Purpose

Campaigns let one design produce many personalized invitation pages.

Example:

```
Campaign
  Template version
  Shared assets
  Recipient dataset
  Variable schema
  -> many invitation publications
```

## 2. Template versus recipient data

The template defines structure and design.

Recipient data defines personalization.

Template:

```
"Dear {{recipient.firstName}},"
```

Recipient:

```
{
  "firstName": "Maria"
}
```

The system resolves the variable into text.

## 3. Allowed variable locations

Variables may appear only in approved fields.

Examples:

- text content
- labels
- URLs generated by the platform
- personalization-safe component properties

Variables must not control:

- component implementation
- arbitrary HTML
- JavaScript
- CSS source
- import paths
- backend queries
- shell commands

## 4. Recipient identity

Each recipient should have an internal stable ID.

Public invitation access may use a random token/slug.

Never expose sequential database IDs as the sole public authorization mechanism.

## 5. Campaign generation strategies

### Shared artifact

Use when only data changes.

```
one renderer output
+
recipient data lookup
```

### Materialized artifacts

Use when recipient pages need to be completely static.

```
template + recipient
 -> artifact per recipient
```

The platform should support both internally but choose the cheaper safe strategy automatically where possible.

## 6. Security

Recipient data is sensitive by default.

Public URLs should reveal only fields necessary for that recipient's experience.

A recipient must not be able to modify a URL to access another recipient.

## 7. Batch operations

Batch generation should be asynchronous.

```
campaign created
 -> validation
 -> batch job
 -> recipient jobs
 -> progress
 -> completion
```

Progress should be resumable.

If 7 of 100 recipients fail, the system should not require rebuilding the successful 93.

## 8. Import

Initial import may support CSV.

Validate:

- headers
- required columns
- encoding
- row count
- duplicate recipients
- invalid values
- maximum size

Show a preview before committing.

## 9. Variable schema

A campaign should explicitly declare allowed variables.

Example:

```ts
{
  recipient: {
    firstName: "string",
    tableNumber: "string"
  }
}
```

The template compiler validates every variable reference against this schema.

## 10. Campaign versioning

A campaign should reference a specific template version.

Changing the template does not silently modify already published invitations.

A new campaign/template version can be generated explicitly.

## 11. Analytics

Campaign analytics may aggregate:

- page views
- unique visits
- RSVP
- completion
- interaction events

Do not expose one recipient's private analytics to another recipient.

## 12. Failure recovery

Batch generation must support retrying individual failed recipients.

The campaign state should expose:

- total
- queued
- processing
- completed
- failed
- cancelled

## 13. Cancellation

A campaign generation job can be cancelled.

Cancellation must be cooperative and idempotent.

Already published recipients remain published unless explicitly unpublished.
